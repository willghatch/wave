** Analysis

- *Multibuffer vs atomic:* Multibuffer beats atomic on 128 x 128 x 32768, S=4 (if MBSK outlier is ignored as a one-off).  On 1024 x 1024 x 8192, multibuffer is much faster than atomic (507.79 us vs 930.71 us) though both lose to baseline.  On most other configs atomic is slightly faster or comparable to multibuffer; multibuffer never beats baseline on large MN cases here.
- *MBSK vs atomic:* MBSK is slower than atomic on every configuration in this run except the suspect 128 x 128 x 32768 row, where MBSK reports ~5969 us (~29x slower than atomic) despite status =ok=.  That single point should be re-timed (possible stall, power state, or measurement glitch).  Ignoring that row, MBSK is not faster than atomic anywhere.
- *vs baseline:* Baseline wins on most medium/large MN shapes.  Split-K wins clearly on skinny 128 x 128 cases with large K (65536 and 32768), especially atomic.  Small K (256 x 256 x 512) punishes all split-K variants.
- *Where non-atomic split-K helps most:* The multibuffer second-kernel design removes atomic contention on C; the largest practical win over atomic in this set is 1024 x 1024 x 8192.  For skinny-tall K, atomic split-K remains the best split variant; multibuffer is competitive on 128 x 128 x 32768.

** Recommendations (step 4)

1. *Prioritize atomic split-K* for the 128 x 128, very large K regime where it already beats baseline (~2.1x on 65536, S=8).
2. *Investigate and optimize multibuffer* for large-tile problems where atomics hurt (e.g. 1024 x 1024 x 8192): multibuffer is ~1.83x faster than atomic there but still ~1.89x slower than baseline; closing that gap is a concrete target.
3. *Treat MBSK as transitional:* fix correctness/sync path if needed, then re-benchmark; current kernel is slower than atomic and shows one anomalous timing—verify before investing in MBSK-specific tuning.
4. *Re-run* the 128 x 128 x 32768 MBSK case in isolation to confirm whether ~5969 us is reproducible.
